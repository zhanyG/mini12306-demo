# mini12306 项目梳理

## 1. 项目简介

`mini12306` 是一个面向软件工程基础实验场景的简化售票系统项目。根据仓库现有文档和当前目录结构，项目已经从早期的单体后端 Demo，演进为一个包含后端服务、乘客端 Web、管理端 Web 的前后端分离系统。

当前仓库主要由三部分组成：

- `demo/`：Spring Boot 后端，负责用户、乘客、车次、订单和管理员相关接口。
- `frontend/`：乘客端 Web，面向普通用户完成注册、登录、查票、购票、订单和乘客管理。
- `front-manage/`：管理端 Web，面向管理员完成车次、用户、订单等后台操作。

这份文档的目标不是替代详细 API 文档，而是为刚接手项目的人提供一份统一入口，帮助快速理解项目结构、运行方式、功能边界和当前状态。

| `数据库接入文档.md`    | 数据持久化说明 | 记录从内存存储迁移到 MySQL 的改动                          |

可以把整个仓库理解为下面的关系：

```text
mini12306/
├─ demo/           # 后端 API 与业务逻辑
├─ frontend/       # 乘客端 Web
├─ front-manage/   # 管理端 Web
├─ docs/           # 过程文档与说明材料
├─ README.md
├─ 后端开发文档.md
└─ 数据库接入文档.md
```

进一步看三个子系统的主要结构：

- 后端 `demo/` 以 `config`、`controller`、`entity`、`repository`、`request`、`service` 为主，符合典型 Spring Boot 分层结构。
- 乘客端 `frontend/src/` 主要包含 `api`、`components`、`composables`、`router`、`utils`、`views`。
- 管理端 `front-manage/src/` 与乘客端类似，额外包含 `layouts` 目录用于后台布局。

## 3. 技术栈

### 后端

根据 `demo/pom.xml` 和现有文档，后端技术栈包括：

- `Java 17`
- `Spring Boot`
- `Maven`
- `Spring Web MVC`
- `Spring Data JPA`
- `MySQL`
- `Lombok`
- `Spring Validation`
- `spring-security-crypto`

当前后端通过 JPA + MySQL 做持久化，不再使用最早版本中的纯 `ArrayList` 内存存储方案。

### 前端

两个前端子项目的技术栈基本一致：

- `Vue 3`
- `Vue Router 4`
- `Axios`
- `Vite 5`

其中：

- 乘客端 `frontend/` 默认开发端口为 `5173`
- 管理端 `front-manage/` 默认开发端口为 `5174`
- 两个前端都通过 Vite 代理将 `/api` 请求转发到后端 `http://localhost:8080`

## 4. 功能概览

### 4.1 后端能力

结合现有文档和目录结构，后端当前主要承载以下几类能力：

- 用户相关：注册、登录、用户信息查询
- 乘客相关：乘车人信息维护
- 车次相关：车次列表、搜索、管理端维护
- 订单相关：购票、退票、订单查询、管理端维护
- 管理员相关：管理员登录、仪表盘统计、后台 CRUD

从目录上看，后端已经包含普通控制器和管理员控制器两套入口：

- 普通接口主要位于 `controller/`
- 管理员接口主要位于 `controller/admin/`

### 4.2 乘客端能力

根据 `frontend/src/router/index.js` 和开发记录，乘客端当前包含这些主要页面与流程：

- `/login`：用户登录
- `/register`：用户注册
- `/`：车次查询列表
- `/buy/:trainId`：购票确认
- `/orders`：我的订单
- `/passengers`：常用乘客管理
- `/profile`：个人中心

从已有文档可以确认，乘客端已经覆盖比较完整的基础购票流程：

- 注册与登录
- 查询车次、按起终点搜索
- 选择乘客并购票
- 查看订单与退票
- 维护常用乘客
- 查看个人信息

`docs/beta1.4-开发记录.md` 还说明，乘客端在测试体验上做过一些优化，例如测试环境下简化身份证输入、支持快速添加乘客等。

### 4.3 管理端能力

管理端是 `beta1.4` 阶段引入的独立 Web 应用。根据 `front-manage/src/router/index.js` 和开发记录，当前主要页面包括：

- `/login`：管理员登录
- `/`：仪表盘
- `/trains`：车次管理
- `/orders`：订单管理
- `/users`：用户管理

结合现有文档，管理端主要提供：

- 管理员登录和退出
- 仪表盘统计信息查看
- 车次增删改查
- 用户增删改查
- 订单增删改查
- 代客下单、订单状态维护等后台操作

## 5. 运行方式

### 5.1 启动前准备

根据 `数据库接入文档.md` 和当前配置，项目已经使用 MySQL 做数据持久化，因此在启动前需要先准备数据库环境。

当前 `demo/src/main/resources/application.properties` 中可以确认：

- 数据库名：`mini12306`
- JDBC 地址：`jdbc:mysql://localhost:3306/mini12306`
- JPA 策略：`spring.jpa.hibernate.ddl-auto=update`

已有文档建议先创建数据库：

```sql
CREATE DATABASE mini12306;
```

说明：现有文档中提到密码应通过环境变量传入，但当前仓库配置文件中已经直接写入了数据库账号与密码。因此在实际运行时，应以当前 `application.properties` 为准，并结合本地环境自行核对数据库连接是否可用。

### 5.2 后端启动

```bash
cd demo
mvn spring-boot:run
```

默认监听端口：`8080`

### 5.3 乘客端启动

```bash
cd frontend
npm install
npm run dev
```

默认访问地址：`http://localhost:5173`

前端通过 Vite 代理把 `/api` 和 `/hello` 转发给后端 `8080`。

### 5.4 管理端启动

```bash
cd front-manage
npm install
npm run dev
```

默认访问地址：`http://localhost:5174`

管理端也通过 Vite 代理把 `/api` 请求转发给后端 `8080`。

### 5.5 前后端关系

整个系统的本地开发形态可以概括为：

- 后端服务提供统一业务 API 和数据库访问
- 乘客端调用普通用户相关接口
- 管理端调用 `/api/admin/**` 管理员接口
- 两个前端都依赖后端正常启动后才能完成完整业务流程

## 6. 数据与权限模型

### 6.1 数据存储

从项目演进看，数据存储经历了两个阶段：

- 早期阶段：使用内存集合存储，重启后数据丢失
- 当前阶段：使用 MySQL + JPA 持久化存储

现有文档中明确提到当前主要会涉及以下数据表：

- `users`
- `passengers`
- `trains`
- `orders`
- `tickets`

JPA 配置为 `ddl-auto=update`，意味着应用启动时会根据实体变化自动更新表结构。

### 6.2 初始化数据

根据现有文档，项目启动后会补充部分初始化数据：

- 若车次表为空，会插入测试车次数据
- 会自动创建默认管理员账号

已有文档中提到的默认管理员账号为：

- 用户名：`admin`
- 密码：`admin123`

### 6.3 权限与鉴权

根据文档和当前前端路由逻辑，系统存在普通用户与管理员两套入口：

- 普通用户通过乘客端登录，前端使用 `localStorage.token` 判断是否已登录
- 管理员通过管理端登录，前端使用 `localStorage.adminToken` 判断是否已登录

根据 `beta1.4` 开发记录，管理员接口使用 `/api/admin/**` 路由，并通过服务端拦截器和内存 token 做鉴权。

这意味着当前权限模型具备基础角色区分：

- `USER`：面向普通购票流程
- `ADMIN`：面向后台管理流程

## 7. 版本演进摘要

### beta1.1

项目完成了早期后端基础结构，建立了 `entity-service-controller` 分层，并提供了简单的增删改查和 API 接口。

### beta1.2

项目从纯内存存储迁移到 MySQL 持久化，后端引入 JPA 和 Repository，数据层实现方式发生了明显重构。

### beta1.3

现有说明中提到这一阶段主要进行了部分代码注释与结构优化思考，但并未形成明确的大版本交付。

### beta1.4

这是当前仓库形态最关键的一次演进，主要体现在：

- 新增乘客端 Web 并完善购票相关页面流程
- 新增独立管理端 Web
- 新增管理员登录、鉴权和后台接口
- 支持车次、用户、订单的后台 CRUD
- 项目从“后端 Demo”演进为“前后端分离的完整演示系统”

如果从接手视角理解，`beta1.4` 代表项目已经不再只是接口实验，而是具备了一个可演示、可交互、可后台维护的完整雏形。

## 8. 当前已知限制

以下限制均来自现有文档整理与归纳，不代表新增设计判断：

- 管理员 token 目前为内存态，服务重启后会失效，需要重新登录。
- 部分复杂边界场景的业务校验仍不完整，尤其是订单状态切换时的一些边界处理。
- 管理端列表尚未做分页，数据量增大后表格性能和可读性会受到影响。
- 乘客端和管理端样式、组件仍各自维护，尚未抽取共享组件层。
- 早期文档中提到过部分异常处理、参数校验、认证能力仍有简化实现；随着项目演进，其中一部分已经改善，但整体上仍更适合作为课程实验或演示系统，而不是直接投入生产环境。
- 当前仓库中的数据库连接信息直接位于配置文件中，这种做法适合本地实验，但不适合作为正式环境配置方案。
